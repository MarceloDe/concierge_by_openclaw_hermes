## 1. Executive summary — the pivot

The current MVP is a **restricted-context planner**: a single `llm_decision` node advises routing, but it operates inside a lattice of deterministic pre-deciders — a keyword regex classifier that defaults every unmatched message to `enrollment_portal_depuration` (`src/concierge/classifier.mjs:25-29`), a curated `classify_intent` graph node (`src/concierge/langgraphRunner.mjs:766-854`, registered at `:3478`), a journey-planner mapping layer, a frozen 8-workflow enum triplicated across code (`src/concierge/llmOrchestrationDecision.mjs:5-14`, `src/concierge/promptContracts.mjs:7-16`), and a router fallback chain that silently regex-routes when the planner's output is invalid (`src/concierge/langgraphRunner.mjs:1403-1406`). This violates the founder mandate that "deterministic code must not silently decide ordinary free-text healthcare/insurance intent when a model is available" and that regex is "not final workflow authority for general chat" (`docs/FOUNDER_IMPLEMENTATION_PROMPT_TEMPLATES.md:96`).

The pivot replaces this with a **3-layer decision architecture** in which the LLM planner is the single workflow authority inside deterministic safety rails. (These are the PROMPT layers — how the planner's context is assembled; the pivot's three DATA layers, which the planner routes across, are the canonical `data_layer` enum — see the header terminology note and the Aetna/UM case below.)

- **Prompt layer 1 — Constitution (code):** identity, hard safety prohibitions, JSON-only output, and a single-source decision contract (`DECISION_CONTRACT_V2`) that is both embedded in the prompt and iterated by the normalizer — eliminating prompt/normalizer drift.
- **Prompt layer 2 — Capability & domain surface (DB catalog rows):** the Postgres `capabilities`/`processes`/`process_steps` catalog promptTable (metadata-only, PHI-masked, pointer-only) plus a DB-derived allowed-workflow list — replacing every hardcoded enum and code-pinned capability list.
- **Prompt layer 3 — Turn context (per-turn hydration):** masked input, messages-channel history, policy result, Redis pointer manifests, checkpoint resume plan, consent/auth state — assembled per turn by the existing payload builder, mechanism unchanged.

Deterministic code keeps exactly what the founder rules permit (`docs/FOUNDER_IMPLEMENTATION_PROMPT_TEMPLATES.md:86-94`): emergency/handoff safety, credential/2FA/captcha/form-submit boundaries, PHI redaction and egress policy, schema validation, approval tokens, source-pointer validation, audit and retention. Everything else — intent, workflow, process offer, tool selection, workflow graph — moves to the planner, validated deterministically **after** the LLM (risk-tier floor, workflow-graph step validation, allowed-workflow check), and failing **loud** (escalate or clarify) instead of silently regex-routing.

> **The Aetna/UM case (from `docs/THREE_LAYER_PIVOT_RATIONALE_AETNA_UM.md`).** The concrete pilot: a University of Miami employee on a UM Aetna plan. **Data layer 1 (public, no auth):** Aetna's Transparency-in-Coverage MRFs published monthly at the public self-insured MRF portal `health1.aetna.com` (see also `transparency.aetna.com`; multi-GB JSON, every negotiated in-network rate per NPI/TIN and CPT code, no member-specific cost sharing); Aetna's public FHIR R4 Provider Directory API (Da Vinci PDex Plan-Net, client-credentials token, no member auth); UM's public SPDs/benefits grids/Welcome Books at `hr.miami.edu` (four medical plan options incl. HRA and HSA variants); CMS Public Use Files (Exchange PUFs, formulary/provider crawls). This layer covers provider search, plan comparison, formulary lookup, cost estimates, benefits education, and public prior-auth documentation requirements. **Data layer 2 (member-authorized read):** Aetna's live CMS-mandated Patient Access API — register at `developerportal.aetna.com`, member OAuth2/SMART-on-FHIR authorize at `apif1.aetna.com/fhir/v1/fhirserver_auth/oauth2/authorize`, scopes `launch/patient patient/*.read` + `offline_access` — serving ExplanationOfBenefit (full claims history), Coverage (plan, member ID, group, effective dates), Patient, Observation, and (expanding under CMS-0057-F, required Jan 2027) prior-auth decisions. **Critical caveat:** UM likely operates a SELF-FUNDED plan with Aetna as TPA; Aetna's Patient Access API covers fully insured Commercial plans in production, so whether UM's group is in scope MUST be validated during developer-portal registration — if not, portal scraping is the fallback for that layer only (§9). **Data layer 3 (portal control):** OpenClaw browser automation ONLY where no API exists — claim submission with attachments, live claim status before the EOB reaches FHIR, appointment scheduling, employer-portal enrollment actions, EOB PDF download — session-based credential delegation (in-session auth pass-through, never credential storage), always gated by explicit user confirmation. Bottom line per the rationale doc: pre-index the public layer into RAG; SMART on FHIR is the primary personalized data pipe (legally cleanest, most stable, CMS-mandated); reserve portal scraping for real-time actions with no FHIR equivalent. The already-verified in-repo motivating evidence stands: the planner's current-balance rule (`src/concierge/llmOrchestrationDecision.mjs:269` — real-time figures require authenticated portal evidence, never research), the Aetna-only portal evidence allowlist (`src/concierge/portalEvidenceVerifier.mjs`), and the read-only/approval-gated worker contract (`docs/adr/ADR-002-execution-v2-llm-manager-worker.md`).

The plan also lands the external data rails the pivot needs — provider directory, MRF pricing, formulary, eligibility, PA-packet preparation — as in-process facade modules and batch pipelines (never MCP servers, never scaffolds), with all signature-gated connectors in the **latest** phases (§9, §11).

## 7. Tool & worker registry mapping table

### 7.0 Capability Registry vs Executable Tool Catalog vs Planner Exposure Contract (founder decision, 2026-07-02 — normative)

The founder's global architectural decision (spine YAML `architectural_principle`) defines three SURFACES: a **Capability Registry** (durable roadmap — MAY contain unimplemented capabilities; visible to coding agents, docs, evals, planner policy; NO dispatch authority), an **Executable Tool Catalog** (runtime dispatch truth — only real, backed, credentialed, tested, policy-gated tools), and a **Planner Exposure Contract** (what the planner may say/prepare when a capability exists conceptually but cannot execute). The storage realization below honors BOTH this decision AND this plan's no-parallel-dispatch-registry rule: **ONE storage, TWO authority surfaces, ZERO parallel dispatch paths.**

- **One storage.** The registry and the executable catalog share the EXISTING `capabilities` table (`schema.mjs:1223` — `capability_key`, `kind`, `status`, `lifecycle_state`, `planner_metadata_json`, `tool_key` FK → `tool_registry(tool_key)`) and its backing tables (`tool_registry` at `schema.mjs:445` with `integration_status`/`risk_level`/`approval_required`; `workflow_definitions`; `openclaw_skills`). No new table, no second registry. The table is EXTENDED via `COLUMN_MIGRATIONS` (§5.3 conventions) with four registry columns:
  - `registry_status TEXT` — the 7 spine status values: `planned | contract_ready | blocked_external_enrollment | implemented_dev | implemented_runtime | disabled_policy | retired` (spine YAML `capability_status_values`). NOTE: this is deliberately NOT the existing `capabilities.status` column — that column (`draft`/`active`/quarantine lifecycle) is already load-bearing in `hydrateCapabilityPointer` (`cap.status !== "active"` refusal, `capabilityCatalog.mjs:161-186` region) and keeps its exact semantics; the spine's status vocabulary lands as the new column so no existing gate is resemanticized.
  - `runtime_selectable INTEGER NOT NULL DEFAULT 0` — fail-closed dispatchability boolean, DERIVED per the spine's `capability_status_values` mapping (only `implemented_runtime` ⇒ 1) and per the executable-catalog requirements (real backing implementation, credentials/enrollment present, policy guard allows, acceptance tests pass, audit + PHI redaction implemented, human-approval gate if write, confirmation capture if transaction). This is data-driven policy, never a kill switch (#2).
  - `blocked_by_json TEXT NOT NULL DEFAULT '[]'` — the concrete external/legal/phase blockers (e.g. `external_enrollment_information_receiver_standing`, `phase_92_executor`).
  - `planner_exposure_json TEXT NOT NULL DEFAULT '{}'` — the row's planner exposure contract (`planner_may` / `planner_must_not`, from spine YAML `planner_exposure_contracts`).
- **Seed source.** The spine YAML is the SEED SOURCE for registry rows: `seedCapabilityCatalog` (`capabilityCatalogSeed.mjs:227`, `CAPABILITY_CATALOG_VERSION` bump) is extended so the spine's `capability_registry` entries populate `registry_status`/`runtime_selectable`/`blocked_by_json`/`planner_exposure_json` at boot — the existing fail-loud boot-seed rule (§10 item 26, Phase 84) covers this seeding too.
- **The Executable Tool Catalog is a DEFINED FILTER, not a second store:** the set of `capabilities` rows with `runtime_selectable=1` AND the existing hydration gates (`status='active'`, `lifecycle_state='production'`, `backingEnabled` backing-table-wins check on `tool_registry.integration_status` / `workflow_definitions.status` / `openclaw_skills.status`, `capabilityCatalog.mjs:144-186`). This filtered view is the ONLY thing hydrated as dispatchable and the ONLY thing the dispatch path (§7 dispatch-trigger rules, §4.4 single hydration pathway) ever sees. `hydrateCapabilityPointer` gains the `runtime_selectable=0 → refusal("capability_not_runtime_selectable")` check ahead of backing verification.
- **Planner promptTable exposure (the honest "visible but not executable" state).** Registry rows with `runtime_selectable=0` and `registry_status` in `planned|contract_ready|blocked_external_enrollment` MAY appear in the planner promptTable as explicitly non-dispatchable **planned capability** entries carrying their `planner_exposure_json` contract — so the planner can classify write intent, prepare packets/work orders/instructions, and say "not yet executable by the system", per the founder's #11 decision. The v2 normalizer MUST reject any `selected_tools.capabilityPointers`/`toolPlan` entry that points at a non-selectable row — NEW hard issue `tool_not_runtime_selectable` (same fail-loud family as `workflow_not_allowed`). This replaces the pre-decision dilemma (dishonest enabled-looking row vs total invisibility): non-executability is a first-class DATA state, never an `integration_status` lie, and the backing-status gate is never bypassed.
- **Prohibited (spine YAML `executable_tool_catalog_policy.prohibited`):** fake enabled tools; visible-but-refusing rows that pass the backing gate dishonestly; planner dispatch to a planned capability; write actions without human approval; raw password storage.

One registration spine, kept: `TOOL_REGISTRY` rows (`workflowArchitecture.mjs:84`, applied by `seedRuntimeRegistries` at store initialize) → `kind='tool'` `capabilities` rows (`seedCapabilityCatalog` at boot, FK-enforced) → planner promptTable → `hydrateCapabilityPointer` with `backingEnabled` verification (`capabilityCatalog.mjs:144-186`; `integration_status` must match `/enabled|ready|available|active/` and not `/disabled|deprecated|retired|deferred/`). **No new registry, no new dispatch pathway.** RECONCILED against the draft's full tool catalog (`docs/THREE_LAYER_PLANNER_PROMPT_DRAFT.md` — knowledge/retrieval, member/payer API, mcp_* internal, OpenClaw workers, human interrupts): every draft tool name appears below exactly once. ## 8. Policy / PEMS / compliance mapping

Evolution of the existing deterministic rails — never a second policy engine.

### 8.1 risk_tier (derived-only, one authority)

`deriveRiskTier(policyResult, actionContext)` — new pure function in `src/concierge/policy.mjs`, projecting the two ladders that already exist: the per-check severity ladder in `evaluateInputPolicy` (`policy.mjs:74-151`) and capability-side `risk_level`/`approval_scope` returned by `hydrateCapabilityPointer`, with PEMS maturity (`trusted`, `promotion_status`, `production_driving_allowed`) consulted at hydrate time as a CEILING.

**Unified vocabulary (CONFIRMED against the draft):** the draft's `risk_tier` enum uses exactly these four labels, so the earlier merge decision stands with no rename. The planner-domain 3-value enum (`read_only|approval_required|human_escalation`) and the policy-domain 4-value ladder were merged into ONE 4-value vocabulary used by BOTH the decision contract (§3.3) and the policy floor (the draft's tier examples — e.g. high = claims submission/PA packet/appeal/scheduling/messages/portal writes; critical = cancellations/enrollment changes/payment/ambiguous high-stakes — are prompt guidance in §3.2; the gate-bound semantics below remain the deterministic floor authority): `low` (evidence-only, no interrupt, PEMS shadow-learns) · `medium` (read-only portal/document observation — read-only/document gates) · `high` (irreversible write — consumed single-use bound token only, per `evaluatePortalAction` core `policy.mjs:153-191`) · `critical` (urgent escalation or credential/prompt-injection hard block — handoff/refusal, never tool execution; suppression ordering preserved: hard blocks suppress the urgent bypass).

`risk_tier` is written into `policy_result.riskTier` (floor) and into the decision (`risk_tier`, LLM may only raise). It never persists as a new authority table (**CONFIRMED derived-only — founder #15, 2026-07-02, spine YAML `risk_tier_policy`**): the authorities are the planner decision record, the policy evaluation record, and the `risk_tier_assigned` audit event, which MUST carry `workflow_id, capability_id, risk_tier, reason_code, policy_version, timestamp`. Materialized reporting views/caches are allowed but are NEVER the source of truth and must include `source_event_ids`, `policy_version`, `recomputed_at`. `hydrateCapabilityPointer` gains a tier-ceiling check: a capability whose scope maps above what the turn's satisfied interrupts authorize refuses hydration with a named reason; the tier→scope map is derived from the three gate constants, never free strings.

### 8.2 mcp_policy_guard (single pre-tool-call chokepoint)

New exported `mcpPolicyGuard({tool, actionSchema, targetUrl, approval, sessionId})` in `policy.mjs`, composed entirely of existing primitives: `normalizeWriteActionSchema` (`approvalResume.mjs:41`), the `evaluatePortalAction` fail-closed core, `classifyUntrustedTextRisk` (`policy.mjs:193`) over tool OUTPUT (stamped `safeForInstructionUse:false`), and the `consume*` token functions. Token consumption happens BEFORE any allow verdict (no over-broad approvals, no global write boolean). Every worker/OpenClaw call site that calls `evaluatePortalAction` directly moves to `mcpPolicyGuard` **in the same commit** — the function's core stays as the guard's internal write-gate but ceases to be a public second entry point. It lands now against the existing OpenClaw/worker action path so it is proven live before any MCP transport exists.

### 8.3 Redaction / data minimization

`mcp_phi_redactor` IS the existing masking layer, not a new module: `maskDirectIdentifiers`/`selectModelPayload` (`src/concierge/modelPayloadPolicy.mjs` DB_POINTER tokens) extended so ALL outbound connector/tool arguments pass masking before egress, plus `maskPlannerMetadata`/`assertPlannerMetadataSafe` on catalog metadata and `redactAuditPreview` on audit reads. `MODEL_PAYLOAD_POLICY_VERSION` bumps. Connector payload types (`aetna_patient_access_fhir_request`, `stedi_eligibility_270`, `plan_net_directory_query`) register in `src/concierge/outboundPayloadObservability.mjs`.

### 8.4 Audit

All guard/interrupt/tier decisions write exclusively through `audit()` (single writer, hash chain). New event types follow existing naming so `auditActionKind` auto-classifies: `mcp_policy_guard_blocked`, `mcp_policy_guard_write_token_consumed`, `risk_tier_assigned`, `llm_invalid_decision_no_silent_fallback`, `consent.granted`/`consent.revoked`, `vault.session_cached`. ### 8.5 Interrupts

Per §4.3: five runtime kinds on the one native interrupt; urgent stays a terminal IN-GRAPH rail (`input_policy → workflow_router` short-circuit, `langgraphRunner.mjs:3514` and `:1221-1300`; bypasses `classify_intent`/`llm_decision` but stays inside the checkpointed graph, suppression ordering per `policy.mjs:87`); promotion review stays offline; clarification stays conversational.
